# Constraints and Invalid Values

A **constraint** is a rule in the input model that forbids some combinations of values, such as "Safari runs only on macOS" or "30 February does not exist"; a constraint-aware generator covers every *valid* combination and produces no invalid row {% cite garvin2011casa %}. Invalid values that a system is meant to reject are a separate problem with its own rule (§3). The page assumes the basics from [Combinatorial Testing](index.md): an input model lists each parameter's values, and a **pairwise** suite, such as one generated by Microsoft's PICT tool, contains every pair of values of any two parameters.

## 1. Deleting invalid rows loses coverage

The tempting shortcut is to generate an unconstrained array and delete the rows that cannot run. For example, take a small configuration model:

```text
OS: Windows, macOS, Linux
Browser: Chrome, Firefox, Safari
Language: EN, DE
```

PICT generates 9 pairwise rows; the two marked rows are invalid:

| OS | Browser | Language |
|---|---|---|
| **Windows** | **Safari** | **EN** |
| macOS | Chrome | EN |
| Windows | Firefox | DE |
| Linux | Chrome | DE |
| Windows | Chrome | DE |
| macOS | Firefox | EN |
| macOS | Safari | DE |
| Linux | Firefox | EN |
| **Linux** | **Safari** | **DE** |

The model has 3 · 3 + 3 · 2 + 3 · 2 = 21 pairs, of which 2 (Windows with Safari, Linux with Safari) are invalid, leaving 19 valid pairs. Deleting the two invalid rows leaves 7 rows, and a check of the 19 valid pairs shows two are gone: (Windows, EN) and (Safari, EN). Each appeared only in a deleted row.

Adding the constraint to the model lets the generator avoid the invalid pairs instead:

```text
IF [Browser] = "Safari" THEN [OS] = "macOS";
```

With it, PICT generates 8 rows that cover all 19 valid pairs {% cite microsoft_pict %}. One more row than the 7 left after deleting buys back the lost coverage. Constraints do not always shrink a suite: Hu et al. note that with ACTS the constrained suite is sometimes the same size or larger {% cite hu2020realworld %}.

## 2. Hard constraints need a stronger search

When constraints are many and interlocked, a generator can spend most of its effort on rows that turn out invalid. Garvin, Cohen and Dwyer's CASA combines simulated annealing with a SAT solver that checks each candidate row. On 35 realistic constrained problems, their reworked search ran 90 times faster than their own earlier simulated-annealing generator. Compared with a greedy generator it was slower, but its arrays had on average 25% fewer configurations. Counting both generation and execution, the annealing came out ahead in most cases if one test suite took longer than 21 seconds to run {% cite garvin2011casa %}.

## 3. One invalid value per test

An **invalid** (or error) value is one the system should reject, such as a quantity of zero or an expired coupon. Most such values stop processing with an error message. Put two in one test and the first error hides the second: the second value's handling is never run. This is the **masking effect**: anything that ends a test early, an error message or a failure, hides whatever the test would have exercised after it. The rule is to include at most one invalid value in each test, with all other values valid {% cite grindal2005survey %}.

PICT marks invalid values with `~` and follows that rule:

```text
Quantity: 1, 5, ~0, ~-1
Coupon: none, SAVE10, ~EXPIRED
Payment: card, invoice
```

Of the 10 rows it generates, 4 have no invalid value and 6 have exactly one, such as `~0  SAVE10  invoice`. Six, because each of the three invalid values appears in two rows, once with each value of the other parameters it is paired with. The valid values are still paired with each other in the 4 clean rows {% cite microsoft_pict %}.

## 4. Different strength for different groups

A **mixed-strength** array gives different parameter groups different strengths *t*: higher where parameters are believed to interact, lower, or none, elsewhere. Daoud et al. used it at Tricentis to cover *less*, not more. The form for building test suites had 10 parameters and an original suite of 71 tests, 28 of which were to be replaced. A plain pairwise array replaced those 28 with 15 tests (58 in all). The mixed array required pairs only within three chosen sets of two interacting parameters and replaced them with 9 (52 in all); it found 13 of the form's 14 defects, where plain pairwise found all 14. Per defect found, over both forms, the original tests needed 5.11 hours, pairwise 3.45 and the mixed array 3.39 {% cite daoud2025effectiveness %}. A mixed array is only as good as the guess of which parameters interact.

Raising strength for a group can cost more than expected. In PICT a group is a sub-model, `{ Card, Amount, Currency } @ 3`, and the sub-model's combinations are then combined with the other parameters as if they were the values of one parameter. In a tested model of three payment parameters and three display parameters (Theme with 2 values, the others with 3), plain pairwise needs 13 rows and 3-way for everything 44. The 3-way sub-model with pairwise elsewhere needs 81: its 27 combinations, each paired with the 3 values of Language, need at least 27 · 3 rows {% cite microsoft_pict %}.

## When to use it — and when not

- **Use** constraints whenever a row could not run or would be rejected for a reason other than the one under test.
- **Do not** add a constraint just to cut tests: every rule removes combinations that will then never be tested.

## Limitations

Constraints are written by hand from the specification and can be wrong. A constraint that is too strict removes valid combinations silently, so review the model as you would code.

## How solid is this?

- **Where it comes from.** CASA's evaluation, Grindal et al.'s survey on error values, Daoud et al.'s industrial study, and PICT 3.7.4 runs on the models above {% cite garvin2011casa grindal2005survey daoud2025effectiveness microsoft_pict %}.
- **What is contested.** The 21-second break-even depends on the problems and the greedy tool CASA was compared with.
